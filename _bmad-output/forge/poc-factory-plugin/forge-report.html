POC Software Factory — a Claude Code plugin

A slimmed-down BMad for fast POCs and 1.5–2h interview exercises. The point is to show d2t's mastery of driving Claude Code. The factory is the evidence, and the human's decisions are what the audience watches.

Outcome: HARDENED · 58 memlog entries · Session goal: define the factory process stage by stage

The process

/factory [task] INTAKE (brainstorm) ──┬─ FRAME (greenfield) ─┐ └─ RECON (brownfield) ─┴─► SCAFFOLD (run contract) ─► SPEC ∥ DESIGN ─► [gate] ─► SLICE PLAN ─► [gate] ─► BUILD LOOP per slice (builder ⇄ reviewers, pipelined, ≤2 rounds) ─► WRAP ─► [human merge OK] budget clock @ ~1:20 → "cut & wrap?"

Locked decisions

loop
  • Conductor /factory; resumes from disk; per-stage skills; rework
  • One file per agent, verdict on the first line
  • Builder on Opus, resumed; reviewers on Sonnet; reviews pipelined
  • One dev server per run, shared by the reviewers
  • Spec fits one screen; every acceptance criterion carries its own check
reviewers
  • No nitpicks. Each finding needs a concrete failure scenario.
  • Categories: bug, spec miss, security, breakage
  • code always; security, ux, a11y and ui chosen per slice by tag
  • ux, a11y and ui test the running app; ui compares against a reference
  • Designer: a single design.md, inherit or invent, at most one question
human
  • Escalates only for: scope change · irreversible or outward-facing action · not converging · taste
  • Two planned gates: spec+design, then the slice plan
  • Every merge needs your OK; the factory resolves conflicts and re-tests first
truth
  • Hooks record facts; a state-machine CLI records meaning
  • A JSONL log for each writer, kept in ~/.factory, outside the repo
  • The dashboard shows each item as claimed or verified. It's our own build, with no Docker.
  • Parallelism is shown by replaying a recorded run, never live

Rejected, and why

  • Forking agents-observe: it needs Docker, is built server-first, and doesn't track pipeline stages. We build our own and borrow its patterns.
  • OpenTelemetry as the dashboard source: it can't name custom subagents and doesn't know which worktree an event came from.
  • Putting the factory's tooling in the project's dependencies: it would pollute the interviewer's repo.
  • An approver agent that merges by itself: every merge needs the human's OK.
  • A "notes" tier for minor findings: no nitpicks, not even logged.
  • Two separate pipelines: one pipeline that forks only at the start.
  • .factory/ state inside the repo: breaks under the sandbox, git clean, and bare-repo layouts.
  • Running parallel worktrees live in an interview: too risky; replay a recorded run instead.
  • A heavyweight BMad UX stage: it can't fit in a 2-hour budget.

Weak points that survived scrutiny

  • The timing is marginal. The tabletop simulation finishes at about 1:50–2:00 with roughly zero slack, and 1:30 doesn't fit. The numbers are estimates, so do timed dry runs on a sample repo.
  • Repo setup is the biggest time sink. Interview repos often need a database or env vars; SCAFFOLD pages the human, but the minutes are still lost.
  • The interview date is unknown, so nobody has checked whether the build order fits the deadline.
  • Accepted on trust in the research. d2t must be able to explain why the dashboard is truthful in their own words.
  • Overlap with ZazenCodes. Credit it openly and lead with the differences: brainstorm first, works on a repo it has never seen, slices, a human OK on every merge, and a dashboard that can prove what it shows.
