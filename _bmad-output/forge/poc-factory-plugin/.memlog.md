- (decision) BMad is the tool used to BUILD the factory; the factory plugin runs standalone in projects without BMad. No coexistence, no competition.
- (direction) Factory = slimmed-down BMad for fast POCs.
- (assumption) Second purpose: showcase how d2t uses Claude Code in job interviews. Possibly in tension with 'fast POC' purpose - unresolved.
- (decision) Interview format = 1.5-2h exercise: either add a feature to an existing codebase OR start a project from scratch. Factory must handle both.
- (decision) Interview and fast-POC goals share one constraint: brief -> working result in ~1.5-2h with explainable human gates.
- (note) PARKED: visibility features - user wants them, to be discussed later.
- (crack) Feature-add exercise = brownfield on an unfamiliar (interviewer's) codebase. Slimmed BMad greenfield flow doesn't cover codebase orientation.
- (lock) Process skeleton: INTAKE -> fork (greenfield FRAME | brownfield RECON) -> SPEC -> SLICE PLAN -> BUILD LOOP -> WRAP. One pipeline, fork only at start; both branches emit same context artifact.
- (lock) BUILD LOOP = builder + reviewers; reviewers can retrigger the builder.
- (decision) Human-in-the-loop with a HIGH escalation bar - most escalations resolved by agents, only human-worthy ones reach d2t.
- (crack) 'Human-worthy' undefined; builder<->reviewer retrigger has no termination rule -> risk of infinite loop or burned time budget.
- (lock) Reviewers do NOT nitpick. Only bugs and serious issues are raised. Time-boxed context (interview / fast POC) overrides polish.
- (kill) Killed 'log' tier for minor findings - nits are not generated at all, not even logged.
- (lock) Reviewer charter: report only with concrete failure scenario, in categories Bug / Spec miss / Security (real exploit path) / Breakage (brownfield: failing tests or convention a maintainer would reject). All reported findings are must-fix; max 2 builder retrigger rounds per slice.
- (lock) Escalation to human ONLY when: (1) scope/intent change or spec ambiguity forking the code; (2) irreversible/outward action - migrations, deleting code outside slice, secrets/network/deploy; new deps page only in brownfield; (3) non-convergence - same finding bounced twice or slice over time box; (4) builder/reviewer taste disagreement (correctness disputes decided by tests).
- (direction) Reviewer roster: reviewer-security, reviewer-ux, reviewer-ui, reviewer-code, reviewer-a11y. Selectable on/off per task.
- (crack) UI/UX reviewers reading code without seeing the rendered app will guess, and UI 'looks off' findings are taste - clash with the concrete-failure charter.
- (lock) ui/ux/a11y reviewers review the RUNNING app (browser automation), not just the diff.
- (decision) Add SCAFFOLD step at start: greenfield installs required components (e.g. Playwright); brownfield verifies required components are present.
- (note) OPEN: reviewer-ui separate (reviews vs a reference/design system) or merged into reviewer-ux? Unanswered.
- (crack) Brownfield: installing factory tooling (Playwright etc.) into interviewer's repo = dependency add -> pages human (rule 2) and pollutes their repo.
- (lock) Factory tooling (browser driver, a11y engine) ships with the plugin (MCP servers, npx), not in project deps. Brownfield: prefer the repo's own e2e tooling (Playwright/Cypress/Selenium) when present; fall back to plugin tooling.
- (lock) SCAFFOLD sits after FRAME/RECON, before SPEC; emits a run contract (install, start, URL/port, test cmd, health check). Greenfield: create project + own test runner. Brownfield: install nothing; verify install/start/tests pass; page human if broken.
- (assumption) d2t assumes most UI projects already ship e2e tooling. Likely false for interview starter repos (often unit-test only) - hence fallback.
- (lock) Reviewer roster+selection: code always; security on slices tagged input/auth/secrets/external; ux + a11y on UI slices (running app); ui on UI slices ONLY when a reference exists (repo component lib/design system or UI kit chosen in FRAME), else its broken-rendering checks fold into ux. Tags set per slice in SLICE PLAN; human can override at INTAKE.
- (lock) /factory is the conductor. Entry: '/factory' or '/factory <optional task prompt>' (e.g. '/factory add about button'). Gates after SPEC and after SLICE PLAN; per-stage skills re-runnable; builder+reviewers are subagents; state on disk; '/factory' resumes.
- (lock) INTAKE = conversational brainstorm with d2t before the spec is written.
- (lock) The moment work touches files, the run moves into a git worktree - so multiple /factory runs can work in the same repo in parallel.
- (note) WOW FACTOR section has 2+ parts: (1) conductor/worktree parallel runs, (2) UI behind the factory (= the parked visibility branch).
- (crack) Parallel runs collide: dev-server ports, per-worktree dependency installs (minutes), shared DB; and nobody owns merging N branches back. Greenfield worktree needs a repo with >=1 commit. Resume must know which run.
- (lock) Run ends at WRAP with merge needing explicit human OK. Target is either a PR or a local merge to main. Factory resolves conflicts itself; human gives the final OK.
- (lock) Worktree created at first write (greenfield: SCAFFOLD after git init + initial commit; brownfield: install/verify). INTAKE/RECON/SPEC read-only in main checkout; RECON map shareable across runs. Per-run id, branch factory/<slug>, per-run port in run contract; shared-store installs.
- (decision) After factory conflict resolution: re-run tests + reviewer-code on resolved files before asking human OK; show resolutions in summary.
- (lock) Factory UI = local web dashboard launched by the plugin. WINDOW first (read-only): all runs across worktrees as lanes - stage, current slice, reviewer verdicts, escalation queue. Reads only .factory state so it can't drift. Becomes a cockpit only if acting there beats the terminal.
- (crack) Truth of dashboard depends on state actually being written. LLM conductor self-reporting is unreliable; per-worktree state is scattered - dashboard needs one place to find all runs.
- (note) Event capture design (hooks for facts + schema-enforced conductor events + per-run events.jsonl in main checkout) NOT locked - d2t asked for research on best approach first.
- (note) Research: plugin hooks fire inside subagents with agent_id/agent_type (confirmed); OTel can't name custom subagents and has no worktree identity -> optional cost/token cross-check only. Closest prior art: simple10/agents-observe (plugin, hooks->server->SQLite, Docker, no worktree/pipeline semantics); disler's demo drops events if server down.
- (crack) Original event design weaknesses: hooks don't know run id; plugin hooks fire for ALL sessions in repo; concurrent appends to one file; sandbox may block worktree->main writes; git clean/bare layouts break .factory in main checkout; conductor can lie or forget; crash = no SessionEnd; transcripts expire (~30d) and may hold secrets.
- (direction) Revised: facts via async plugin hooks; semantics via factory CLI as STATE MACHINE (rejects illegal transitions, gate pass checks evidence) + Stop hook blocks conductor in non-terminal state; session->run registry, unregistered sessions dropped; per-writer JSONL source of truth outside repo, SQLite rebuildable cache, no required collector; claimed vs verified display; liveness from heartbeat + 'claude agents --json'; snapshot+redact transcripts at WRAP for replay.
- (lock) Observability design: async plugin hooks for facts; factory CLI as state machine for semantics (illegal transitions rejected, gate pass verifies evidence, Stop hook guards non-terminal exit); session->run registry, unregistered dropped; per-writer JSONL at ~/.factory/<repo-hash>/runs/ as source of truth, SQLite rebuildable cache; dashboard shows claimed vs verified; liveness via heartbeat + claude agents --json; WRAP snapshots+redacts transcripts for replay. OTel optional for cost/tokens. Use native claude --worktree (.claude/worktrees/<name>).
- (note) SPIKE before build: env var inheritance into hooks; plugin agent_type naming; sandboxed writes to ~/.factory.
- (crack) d2t accepted observability design on trust in research. Interview risk: must be able to explain why the dashboard is truthful in own words.
- (lock) Dashboard: build our own, minimal (no Docker, tiny local process, JSONL->SQLite cache, SSE). Built by BMad as part of building the factory - NOT the factory's first job. Borrow agents-observe patterns, not code.
- (note) Prior art reviewed: zazencodes software-factory-claude-code (1 skill + 7 agents: spec-writer, builder, 4 reviewers, approver; job.json per job written by orchestrator; worktrees ../<repo>-factory/<id>; per-job ports; agent-browser CLI; polling dashboard.html; backlog + /factory next/approve/rework; MAX_RESUMES=2; approver auto-merges or ESCALATEs).
- (lock) Borrow from ZazenCodes factory: one-file-per-agent with first-line verdict protocol (VERDICT/STATUS/APPROVE|ESCALATE); spec Assumptions section checked for product decisions; acceptance criteria each with a command/page check; resume same builder via SendMessage; agent-browser --session per job+reviewer (evaluate vs Playwright MCP in spike); atomic mkdir job claim; /factory rework <note> (+ backlog/next); model routing by role. Inspired-by is fine - credit openly.
- (direction) Differentiators vs ZazenCodes: brainstorm-first intake; RECON + run contract for never-seen repos; slices; human OK on every merge (approver only prepares); hook-verified dashboard (claimed vs verified); shipped as plugin; greenfield path; a11y lens.
- (lock) Build order: dashboard moves earlier (right after the walking skeleton).
- (direction) New agent: ux/ui designer. Inherit mode (existing UI -> extract) or invent mode (new). Based on BMad UX (DESIGN.md + EXPERIENCE.md) but far lighter - must fit in the <2h run.

Inherit mode (brownfield: extract from repo, no questions) or invent mode (greenfield: UI-system defaults e.g. shadcn, max ONE question with 2 options + default, rest [ASSUMPTION]). ~10 min, runs parallel to SPEC, approved at the SPEC gate. Skipped when no UI-tagged slices. Gives reviewer-ui a reference whenever it ran.
- (lock) Build order: 1 skeleton; 2 truth layer + dashboard; 3 loop + charter + all reviewers + designer; 4 worktrees + parallel; 5 greenfield + slices + replay.
- (decision) Target: 1:30-2:00 per feature. Interview wow = dashboard + claiming worktree/parallel capability; d2t will NOT run parallel worktrees live (risk).
- (note) Tabletop simulation (brownfield interview, estimates): intake+recon+scaffold+spec/design+gates ~T+35-40; per slice clean ~18-22m, with 1 rework ~25-30m; 3 slices -> T+110-130 incl. wrap. Fits 2:00 marginally, not 1:30.
- (crack) Sim bottlenecks: serial review rounds per slice; each reviewer starting own dev server; long specs at human gate (ZazenCodes spec ~8KB); Opus everywhere; unbudgeted interviewer interruptions/scope change; repo setup (DB/env) failures at SCAFFOLD.

- (lock) Sim-driven changes: (1) pipelined reviews - slice N reviewed while builder starts N+1; (2) one dev server per run from SCAFFOLD, shared by reviewers, separate browser sessions; (3) spec fits one screen, detail in acceptance criteria; (4) budget clock - at ~1:20 conductor proposes cutting remaining slices (a gate); (5) Sonnet for reviewers+designer, Opus for spec+builder; (6) parallelism shown via REPLAY of a real recorded multi-run session, not live.
