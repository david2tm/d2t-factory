## Intent

**Problem:** Every failed SCAFFOLD check pages the human, even when the factory could fix it itself. In dry run 1, a half-downloaded Puppeteer cache failed `npm ci`, and setting `PUPPETEER_SKIP_DOWNLOAD` would have fixed it (finding 6b; CAP-4).

**Approach:** When a brownfield SCAFFOLD fails only on contract checks (install, health, test) and `SCAFFOLD_REPAIR_ROUNDS` (1) is not used up, `next` resumes the same scaffolder with a repair brief instead of raising the card (AD-8, AD-24). The brief holds the failed checks, their log tails and the repair envelope. A repaired contract is checked again, and a second failure raises `scaffold_failure` with both rounds in its reason. Every contract command gets `FACTORY_CACHE_DIR` = `runs/<run-id>/cache/`.

## Boundaries & Constraints

**Always:**
- **The trigger.** The round runs only when every failure is a `contract.install`, `contract.health` or `contract.test` failure. A tracked-file change, a baseline drift, an exclusive conflict or a copy error raises the card at once, as today. Greenfield runs never get a round: AD-8 puts the round under Brownfield.
- **How the round is recorded.** It is a `step_reissued` of the reported scaffolder. The event's data gains these optional fields, additive within `v:1`:
  - `kind: 'resume'` and `agent_id`, when the agent can be resumed. The rule is the builder's `resumeAgent`: its agent was spawned after the latest `session_bound`. Otherwise the reissue is a spawn.
  - `repair: {failures: string[], checks: string[]}`, which holds the round-1 failure lines (redacted) and the failed check step ids.
- **Rounds used.** Count the `repair` reissues whose new step is not voided.
- **The active repair.** This is the latest `repair` reissue with no `escalation_ruled` after it. A human ruling ends it.
- **The repair brief** (`briefText`, scaffolder only, while a repair is active). It has a `## Repair round` section with:
  - each failure line, and each failed check's log path among the inputs;
  - the previous contract's out.md as an input;
  - the envelope (`review-policy.md` SCAFFOLD repair): change only the contract's commands (env vars, flags, the package-manager command form, timeouts); point tool caches at `$FACTORY_CACHE_DIR`; never delete or edit anything outside the worktree; change no tracked file; add no dependency;
  - the instruction: on a project-side cause (secrets, services, a broken repo), write `STATUS: ESCALATE` / `Scaffold failed: <why>`; otherwise write the whole revised contract.
  - A reissue of the repair step keeps the section: a parse failure, an orphan, or a resume whose agent is gone.
- **Second failure.** The card reason is `round 1: <r1 failures joined "; "> · repair: <diff> · round 2: <failures>`. `<diff>` is generated by the CLI from the two contracts: each changed key as `<key> "<old>" → "<new>"`, joined with `; `, or `no contract change`. The accept rule is unchanged.
- **ESCALATE on the repair step.** The card is raised at once, with reason `round 1: <r1 failures> · round 2: Scaffold failed: <why>`.
- **`FACTORY_CACHE_DIR`.** It is an absolute path from `paths.ts` (`runCacheDir`). It is created before use and set in the env of every contract command the CLI runs (install, test, a health command, and the dev server's `start`). The scaffolder brief states it as a fact. Recordings never copy it.
- **`agents/scaffolder.md` step 6** follows the amended text in proposal §4.4.

**Never:**
- No new event kind, process, route or dependency. No change to stored recordings, to replay, or to any other card.
- The CLI never deletes the cache dir or anything outside the run dir and worktree.
- No repair for greenfield runs, and no repair after a human ruling.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected |
|---|---|---|
| Repair passes | install fails (exit 1); the repaired contract passes all checks | resume issued, no card; scaffolder verified; SPEC starts |
| Repair fails | install fails, the repair's install fails again | one `scaffold_failure`, reason `round 1: contract.install failed (exit 1): … · repair: install "npm ci" → "PUPPETEER_SKIP_DOWNLOAD=1 npm ci" · round 2: contract.install failed …` |
| Repair escalates | health fails, then the repair reports `ESCALATE` / `Scaffold failed: needs a database` | card at once, both rounds in the reason |
| First report escalates | scaffolder ESCALATE in round 1 | card at once, no round (unchanged) |
| Repair dirties the tree | the repair edits a tracked file, and the checks pass | card: `… round 2: tracked files changed in the worktree` |
| Not repairable | install passes; tracked file changed | card at once, no round |
| Agent gone | the resume's SendMessage fails, `done` finds no output | reissued as a spawn; the brief still has the repair section |
| After a human retry | rule `retry` on the round-2 card, then the checks fail | card at once, plain reason (no rounds) |
| Greenfield | a greenfield test check fails | card at once (unchanged) |

## Implementation Notes

- `activeScaffoldRepair(commands)` takes only the command log (it needs no state). The "no repair after a human ruling" rule is `scaffoldRuled(state, commands)`: any `escalation_ruled` on an ask whose subject is a scaffolder step.
- The repair brief gets its section from `BriefExtra.repair` when the repair is issued (the event is not appended yet), and from `activeScaffoldRepair` on every later scaffolder brief. `previous` (the round-1 step id) is brief-only. It is not stored on the event, because the event's `old` already names that step.
- `contractDiff` (next.ts) compares the two reported, redacted contract projections (`output.front`). A non-string value is shown as JSON, and a missing key as `""`.
- A copy_gitignored failure on the repair step takes the ESCALATE path: the reason is `round 1: … · round 2: <copy error>`, with no diff.

## Design Notes

A reissue rather than cancel + issue: AD-24 already treats a ruling's retry of the scaffolder as `step_reissued`, the role slot stays single, and a resume that finds its agent gone already falls back to a spawn. Carrying `repair` on the event marks the round without inferring it from check order. The `repair:` diff comes from the CLI, not from the agent's own account, in line with the truth layer.
